# VibeCheck replacement feature plan — proposed M0-02A contract

This is a **reconstruction**, not the missing original feature plan. It derives from [MASTER_SPEC](../MASTER_SPEC.md) and the product-owner decisions recorded for M0-02A. The master specification wins on conflict. This plan and [the contracts](../contracts/) are proposed implementation boundaries for review, not evidence that any feature exists. No SQL, routes, integrations, or UI are implemented by this document.

## 1. Product and delivery scope

**Product Stage 1** retains the full §7.1 vision: public and authorized private repositories, commit-range analysis, evidence-grounded Code Detective, multiple-choice and written Knowledge Checks, two knowledge tracks, text lessons, Rubber Duck, companion, labeled samples, accessible themes, and honest Plan/Deploy previews. Stage 2 and Stage 3 remain as in the master specification.

**Hackathon Demo MVP critical path:** paste a public GitHub URL without sign-in; read actual bounded repository code; show normalized concepts with file/line evidence and a bounded redacted snippet; explain selected code; generate a short **multiple-choice** Knowledge Check; accept answers with deterministic grading and evidence-grounded feedback; show a guest-session completion result separating demonstrated from unverified concepts. A signed-in user's persistent My Skills belongs to the later Product Stage 1 path. Anonymous attempts are session-scoped and create no persistent knowledge profile. Rubber Duck and companion follow the critical path. Private repositories, persistent user history, and settings require authentication and can follow the public demo. Plan/Deploy are clearly labeled previews. No fabricated analysis, metrics, or execution of arbitrary AI-generated code.

**Outside the Hackathon Demo implementation target:** assessment item reporting, companion messages, analysis cancellation, repository deletion, repository listing/history, private GitHub authorization, written-answer grading, persistent BYOK, billing, persistent AI usage ledger, and Rubber Duck, Plan, and Deploy backends. These remain in Product Stage 1 or later contracts as applicable; their presence in OpenAPI or the domain model does not make them demo prerequisites. Design tokens wait for the separately supplied approved brand inputs.

## 2. Dependencies and milestones

`M0-01 foundation → M0-02A contracts → M0-02B approved implementation planning → public import/analysis → Code Detective → multiple-choice Knowledge Check → guest completion result → later persistent My Skills/Rubber Duck/companion → hardening`. UI and backend can run in separate worktrees after contract review. Product Stage 1 private access, written grading, lessons, reporting, and remaining UI have their own tasks. Do not conflate the demo gate with all Stage 1 release gates.

## 3. Domain and ownership

See [domain-model](../contracts/domain-model.md) for the full product model and smaller hackathon implementation minimum. A `repository` is a user's durable resource or a short-lived guest resource; `analysis_run` is pinned to a commit; `evidence_ref` names immutable file/line provenance and projects a bounded redacted snippet; `repository_concept_evidence` links a taxonomy concept to cited code. `assessment_item` keeps answers and rubrics server-side. `attempt` is append-only. `knowledge_state` is a signed-in user's derived cache, never inferred from commits. The guest completion result is derived from current-session attempts and is not a persistent profile. Every resource is scoped to its user or opaque guest session. A guest session can access public resources only. No direct guest access to Supabase tables is proposed.

## 4. Repository-analysis pipeline

Validate and canonicalize GitHub repository URLs server-side against an explicit GitHub URL allowlist; never fetch arbitrary remote URLs or accept URL credentials. Resolve public accessibility or later per-repository private authorization. Establish source snapshot SHA and bounded commit range (`MAX_ANALYZED_COMMITS=50` initially). List candidate files, skip unsupported/binary paths, reject source files over `MAX_SOURCE_FILE_BYTES=1048576`, prevent path traversal, and budget total work. Fetch with bounded concurrency and timeouts. Detect language; run language adapters and deterministic rules; normalize concepts and evidence; request AI clarification only for ambiguity and after applicable code-sharing consent. Validate cited line ranges against the snapshot before persistence or response. Redact secrets and bound the client-visible snippet to 2,000 characters, indicating truncation. Treat repository files, comments, READMEs, and commit messages as untrusted prompt data. Record skipped-file reasons and partial results honestly. Execute zero analyzed or AI-generated code. Worker lifecycle: `queued → running(stage) → succeeded | failed | cancelled`; retry only safe transient work under lease and idempotency rules. See [language-analysis](../contracts/language-analysis.md).

## 5. Assessment and knowledge

For the demo, generate only multiple-choice questions from evidence refs, validate one defensible key and misconception-tagged distractors, and grade deterministically. Do not send answer keys, rubrics, or withheld explanations before submission. Written evaluation is later Product Stage 1: validated `correct | partial | incorrect`, visibly **AI-graded, reviewable**, with auditable correction rather than in-place attempt mutation. An attempt records `yes | no | prefer_not_to_say` per submission, outcome, feedback, and evidence. Retain attempts append-only for their owner/session lifetime. The latest valid graded attempt for each declared track supplies its state; `prefer_not_to_say` receives feedback as practice evidence and updates neither track. A guest completion result derives `demonstrated` versus `unverified` from the current assessment-session attempts only; it expires with the guest session and never writes `knowledge_state`. Persistent signed-in state remains `unassessed | assessed_correct | assessed_partial | assessed_incorrect`. Commit history and observed concepts alone never establish demonstrated knowledge. States older than 180 days display as stale without erasing history.

## 6. API and state transitions

All application routes use `/api/v1`, JSON `{data,error}` envelopes, stable errors, server-scoped authorization, and cursor pagination where needed. `Idempotency-Key` is required for repository creation, analysis starts, and attempt submission; Code Detective and assessment generation do not require a complex idempotency ledger for the demo. [OpenAPI](../contracts/openapi-v1.yaml) specifies public shapes; [errors](../contracts/errors.md) specifies code/status/retry behavior. Guest calls require an opaque, HTTP-only, short-lived guest session established by the server on first public request. `GET /repositories/{repositoryId}` returns `latestRunId` for navigation recovery; concepts are read by immutable run ID. `GET /assessments/{assessmentId}/completion` derives the guest-session skill result. A guest cannot list account resources, save My Skills, or access private repositories. Rate limits and budgets are stricter for guests. Session and idempotency identifiers never appear in response bodies. Cancellation is a later Stage 1 operation, not a demo endpoint to implement.

## 7. AI boundary and privacy

AI feature → AI service → provider resolver → `AIProvider` → provider adapter. Claude is the initial server-configured managed provider. Future BYOK uses a credential reference to a separate encrypted secret store, never a raw key in ordinary application tables, usage records, logs, or client responses. The service pins prompt/schema versions, validates structured output and evidence, records provider/model and usage/cost metadata, applies budgets, and handles provider failure. User-provided code is untrusted; delimit source from instructions, prohibit model tool access to private data, scan for secrets before any code excerpt leaves the server, and obtain per-repository consent for sending code. No BYOK UI/storage, billing, subscriptions, multiple-provider implementation, or prompt content is part of M0-02A. See [AI operations](../contracts/ai-operations.md).

## 8. Proposed persistence schema

The detailed proposed tables and relationships are in [domain-model](../contracts/domain-model.md). This section replaces the absent original plan's schema pointer; it is not a migration approval. PostgreSQL with Supabase Auth is the intended durable store for later authenticated history. The demo minimum is session/repository state, analysis run, evidence/concepts, assessment, attempts, and derived session completion; it does not require every proposed table or persistent AI usage ledger. Guest data may use short-lived server-managed storage with explicit expiry; the storage mechanism and TTL need implementation review. Authenticated records use RLS plus service-layer ownership checks. Later deletion cascades cover a repository's runs, files, evidence, assessments, attempts, and AI-call references; independently demonstrated user knowledge derived across repositories must be recalculated when source attempts are deleted. Deleting an account removes owned identities, authorizations, repositories, assessments, attempts, knowledge, and usage metadata according to an approved retention policy. Legal/operational exceptions and deletion SLA remain open.

## 9. Errors, limits, and concurrency

Error codes are stable across transports; do not reveal another user's resource existence. `RESOURCE_NOT_FOUND` is used for foreign-owned IDs. Provider/GitHub failures are retryable only when specified in [errors](../contracts/errors.md). Initial configurable caps: 50 commits per run and 1 MB per source file. Additional aggregate byte/file/token/time limits and guest hourly quotas need explicit values before implementation. One active analysis per repository and snapshot is proposed; identical idempotency keys replay the original response, a reused key with different payload conflicts. A worker lease and bounded concurrency prevent duplicate processing. AI result caching must preserve consent and owner boundaries.

## 10. Security, accessibility, and tests

GitHub and AI tokens stay server-side. Private access is neutral between narrowly scoped GitHub App and OAuth; it needs per-repository authorization, revocation, minimum permissions, and no raw credential in ordinary tables. Enforce strict GitHub repository URL validation, forbid arbitrary remote URLs, prevent path traversal, treat source and commit messages as untrusted prompt data, and execute zero analyzed code. Also prevent XSS, unsafe Markdown/HTML, cross-user access, answer leakage, and logging source or secrets. Use WCAG 2.1 AA with sensible 2.2 target-size improvements. Contract-first tests: OpenAPI lint and response schema, forbidden-field checks, errors, guest ownership, consent, required idempotency only where specified, rate limits, GitHub failures, bounded/redacted evidence snippets, AI malformed output, prompt-injection fixtures, deterministic grading, guest completion, and latest-attempt transitions. Tests precede implementation in each later task.

## 11. Open decisions

Master spec §29 still has D-01 through D-10, Q-01 and Q-08. D-09 is the exact retention/deletion SLA; no 30-day policy is approved. Additional implementation decisions: total per-run size/file/token/time budgets; guest quota and TTL/cleanup mechanism; consent wording and provider retention terms; whether anonymous attempts can be resumed across tabs; private GitHub App versus OAuth; human written-grade review workflow; catalog/version policy for taxonomy and prompts; production rate-limit/usage-credit policy. These are proposals requiring approval at the relevant implementation task, not silently adopted product requirements.
